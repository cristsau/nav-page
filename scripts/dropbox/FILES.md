# Personal Dropbox file library

The `/files` page is for the NAV administrator bound to a **separate Full Dropbox app**. The backup App Folder credential is never reused. Only these personal scopes are supported: `account_info.read`, `files.metadata.read`, `files.content.read`, `files.content.write`. No team, sharing, permanent-delete or account-write scopes are required.

## Supported

- Nonrecursive directory browsing, filename search and bounded pagination.
- List/grid presentation, type filters and name/date/size sorting apply **only to loaded items** (folders first). Pagination remains explicit; the count and empty-filter state do not claim a whole-cloud search. Changing a filter clears selection, and select-all only selects visible eligible items. Grid cards use type icons, never background media downloads. View choices and metadata are not persisted in browser storage.
- Read-only details show list metadata, exact bytes/time/revision and explicit name/path clipboard buttons. Folder size is unknown (no recursive scan), and details are a snapshot until the list is refreshed. Clipboard denial offers manual selection.
- Desktop drag-and-drop of up to 50 regular files opens a target/count/size confirmation before queueing. Cancel does not upload. Folder/mixed/unknown-entry drops are rejected rather than flattened; use the separate directory picker. File navigation drops outside the area or while a dialog is open are suppressed without changing drafts.
- Directory selection preserves relative paths after explicit confirmation: at most 50 files, 50 directories and bounded depth. A strictly new root is created, with parents before children; no merging/overwriting. Empty directories are not included by the browser. Invalid/conflicting paths reject the entire plan. Partial directory creation is reported and never blindly retried or auto-deleted.
- Recent history uses stable file ID (up to 20 revisions). Historical paths are also checked against backup protection. Revisions can be streamed for download; up to 20 MiB may be recovered as a **new sibling copy**, with bounded bytes and hash verification. Original content is never overwritten; collision/concurrent source changes stop copying. Bigger versions use download or Dropbox's official recovery UI.
- Deleted-file browser lists **only direct deleted records in the chosen directory**, with explicit pagination; it does not scan the whole cloud or claim parity with Dropbox's recycle bin. Available file revisions (up to 20, exact deleted path and single file lineage) support session-authenticated downloads and new sibling copies up to 20 MiB. Folders, moved/expired/unavailable records and larger recovery operations use the official recycle-bin link. No permanent-delete or in-place restore endpoint exists. Backup paths and ancestors remain excluded. Download handles expire after five minutes, are purpose/owner/connection-bound, and revalidate lineage and backup protection on use.
- Create folders, rename/move/copy without overwrite or ownership transfer. A directory picker replaces manual destination paths. Select up to 50 displayed items for sequential batch move/copy/delete, with individual success/failure receipts; nothing implicitly selects unloaded search results.
- Delete uses an ordinary confirmation dialog, not typed filenames. The server issues a short-lived opaque preview, binds stable IDs and file revisions, and rechecks folder metadata before deletion. Folder deletion includes children (up to 500 descendants, five bounded pages); changed/unknown/oversized trees fail closed. There is no permanent-delete API. The legacy filename-confirmation endpoint remains file-only for older clients.
- Upload queue accepts up to 50 files at once, up to 50 GiB/file, using sequential 8 MiB Dropbox upload-session chunks. No full-file API buffer or staging file. New files are read in 4 MiB browser blocks to calculate their full Dropbox content hash before starting; this extra local read has progress/pause/cancel controls and can take time for movies. Chunk hashes and the final Dropbox content hash/size/path are verified. Strict add never overwrites or auto-renames. Pause/resume/retry/cancel and acknowledged progress are available; after refresh, hash-bound jobs in the same API process can be resumed by reselecting the original file.
- Session-authenticated streaming and single HTTP Range requests for native image/video/audio preview. No public media links, server transcoding, or offline file cache.
- UTF-8 text/Markdown/JSON editing up to 1 MiB, revision-conditional saves, local-in-memory dirty draft retained on conflicts. HTML/SVG are download-only. Office/PDF opens in Dropbox; no embedded Office editor is claimed.

## Connection

Run `Connect-NavDropboxFiles.cmd` on the operator's Windows computer. Confirm the independent application and personal account. PKCE callback: `http://127.0.0.1:53682/dropbox/callback`. Keep public clients allowed. Credentials are encrypted for the current Windows user; no token/secret should be pasted into NAV or chat.

Server installation is a separate authorized operator procedure. The API loads `<NAV_MANAGED_INTEGRATIONS_DIR>/dropbox-files.json`, a regular owner-only file (0600 on Linux, API process UID, no hardlinks/symlink). Schema version 1 requires `purpose=nav-files`, `accessType=full_dropbox`, exact `ownerUserId`, separate `clientId` / `backupClientId`, `refreshToken`, `accountId`, the four scopes, `backupFolderId`, and `backupFolderPath`. This is a private server configuration, never a repository file or environment dump. The connection is reloaded per operation; deletion disables the library without modifying the backup app.

Every operation resolves the backup folder's stable ID and protects both its original and current paths. Ancestors cannot be renamed/moved/copied/deleted. If protection cannot be established, operations fail closed. Simultaneous moves performed outside NAV cannot be made transactional with Dropbox API operations; do not relocate the backup tree or edit a folder being deleted during file operations. A folder snapshot check is not an atomic Dropbox tree lock.

Upload handles are owner/connection-bound (24-hour inactivity expiry, maximum 32 retained sessions). By default they remain in the same API process; optional encrypted persistence below adds restart recovery. The user must select the original file: name and size are checked, then its complete content hash is verified, and an explicit Continue resumes from the server-acknowledged offset. Same-name/same-size changed files are rejected, and the API checks the declared full hash before committing. No file handle, file body or hash is persisted to browser storage. Old sessions without a full identity are not offered for refresh recovery. Connection changes or expiration require a new upload. Mobile browsers may suspend background tabs. Cancellation at a chunk boundary never deletes committed cloud files; uncommitted provider sessions expire remotely. Unknown finish outcomes require manual directory review instead of blind retry. Lost append receipts are reconciled only for the identical pending chunk and exact expected offset.

## Verification and limits

### Encrypted browser-upload progress (development candidate)

The optional `dropbox-uploads.json` configuration enables encrypted per-job progress in `dropbox-upload-state` under `NAV_MANAGED_INTEGRATIONS_DIR`. An authorized Linux operator initializes both with `node <absolute-path>/scripts/dropbox/init-upload-store.mjs <private-integration-directory>`; it refuses overwriting existing or partially initialized state. Do not run this in production until the candidate's Linux/production gates and operation-specific installation are approved. No OAuth, backup key, or user data belongs in this configuration.

Only upload metadata, provider session ID and 4 MiB block hashes are stored (AES-256-GCM, separate random key, per-job authenticated ID, directory 0700/file 0600). No file body is staged. At most 32 jobs; metadata is bounded to 1.3 MB per file even for the logical 50 GiB limit. Pending append intent is saved before the external call; after restart the identical chunk can reconcile a lost receipt. A saved `committing` state becomes review, never an automatic finish retry. Cancellation removes only metadata; no committed cloud file is deleted.

There must be one API writer/PID namespace on this local filesystem: no clustered APIs, shared network filesystem or concurrent containers. A lease checks PID plus Linux boot/start identity; active writers and uncertain/damaged leases fail closed. Graceful close releases it; a verified dead process can be reclaimed. State/key loss or unsafe links/permissions is an error, not an empty-queue fallback. Back up or retain the key and metadata together for API redeployment, but exclude these short-lived session records from long-term cloud backups. Do not delete the config to disguise an initialization failure.

With no configuration, the API explicitly reports `reselect_after_refresh_api_process`. With initialized encrypted storage it reports `reselect_after_restart_encrypted`, and the page shows the correct limitation. Jobs expire after 24 hours of inactivity; changed owner/connection cannot list or resume old jobs. Actual upload-session validity still depends on Dropbox.

Offline uploads use a separate key, state directory and writer lease: `dropbox-offline-uploads.json` and `dropbox-offline-upload-state`. Initialize them explicitly with the same operator command plus the final argument `offline`. This never changes the web-upload namespace or backup OAuth connection. The offline API serializes manager initialization, restores provider cursors and reconciles queue progress with durable upload progress after restart. Identical cached chunks reconcile lost append receipts; an unknown commit remains review. Queue persistence failure blocks further mutations until restart/operator inspection. The dialog reports `encrypted_disk` only when configured. Without configuration, retransmission from worker cache remains the legacy behavior. Run `api/test/offlineUploadPersistence.test.js` and `api/test/offlineDownloads.test.js`; initialization and Linux host boundaries are additionally tested by `scripts/dropbox/control-linux.test.mjs` in a disposable runner.

Run `api/test/dropboxUploadStore.test.js` for restart, persisted lost receipt, corruption, write failure, cancellation, writer exclusion, exited-child lease recovery, owner separation and bounded metadata checks. The hash construction follows the [official Dropbox content hash specification](https://docs.dropboxapi.com/dropbox-api/docs/technical-reference/content-hash).

The offline-download dialog is separate from browser uploads; see [outbound worker](../offline/README.md). Its first node has a 6 GiB staging limit, not the ordinary browser upload limit of 50 GiB. It requires an explicitly configured node, never forwards Dropbox OAuth to that host, and does not enable backup automation.

Run `api/test/dropboxFiles.test.js`, `api/test/dropboxFilesRoute.test.js`, `api/test/dropboxFilesV2.test.js`, `api/test/fileTransferQueue.test.js`, `api/test/filePresentation.test.js`, `api/test/dropboxFileHistory.test.js`, `api/test/folderUploads.test.js` and `api/test/dropboxDeletedFiles.test.js`. `scripts/verify-dropbox-files-ui.mjs` exercises the real Vue component with synthetic API responses, a 25 MiB upload, a reload/reselection/offset recovery scenario, deleted-file browsing and generated WebM, no personal cloud access. Set `NAV_FILES_UI_EVIDENCE`, `NAV_PLAYWRIGHT_MODULE`, and `NAV_BROWSER_PATH` to isolated test locations. Linux file-permission/symlink tests and a separately authorized real multi-chunk synthetic roundtrip must run before release. A logical 50 GiB unit case does not prove a real 50 GiB movie transfer.

Deleted-record contracts follow the [official Dropbox SDK API types](https://github.com/dropbox/dropbox-sdk-js/blob/main/types/dropbox_types.d.ts): `ListFolderArg.include_deleted`, `DeletedMetadata`, `ListRevisionsArg` path mode and `ListRevisionsResult.is_deleted`. Provider retention and record availability determine whether a revision can actually be downloaded. A deleted marker alone is not proof of recoverable file bytes.

Drag implementation references: [MDN file drop](https://developer.mozilla.org/en-US/docs/Web/API/HTML_Drag_and_Drop_API/File_drag_and_drop) and [entry capability](https://developer.mozilla.org/en-US/docs/Web/API/DataTransferItem/webkitGetAsEntry). Browser harness uses explicit synthetic entry objects; actual OS drag and iPhone use still require device acceptance.

Mock tests do not prove a real account is Full Dropbox or a production installation is correct. Real acceptance must verify the exact account/application, bind the existing backup folder, and use only an explicitly authorized synthetic fixture directory for writes. Existing personal files and backup contents are out of the test-write scope. Media compatibility depends on the browser codec; unsupported video falls back to download/Dropbox.

API policy: 120 operation requests/minute and a separate 600 chunk requests/minute budget for the bound owner, four active handlers, two streaming downloads, two concurrent large-body requests reserved before parsing. Each new chunk is at most 8 MiB (legacy direct uploads stay 20 MiB). Requests are not automatically retried on ambiguous mutations. Filenames/content/provider errors, upload handles and raw pagination cursors must not enter operational logs.
