# Personal outbound download node

NAV's file-library **Offline download** dialog accepts public HTTP/HTTPS file URLs and an existing personal Dropbox destination. It does not accept magnets, torrents, login cookies, embedded credentials, nonstandard ports or HTML sharing pages. It never executes downloaded content.

The first node is resource-limited: one active job, 6 GiB/file, 2 MiB/s download, at least 2 GiB reserved filesystem space, ten queued jobs and fifty retained records. A paused/failed job keeps its cache and blocks subsequent work until continued/cancelled. URLs must supply a bounded Content-Length; HTTP resume requires a matching strong ETag and exact range, otherwise a full 200 response restarts safely. Every redirect is DNS-resolved and pinned; private/reserved IPv4, infrastructure targets, IPv6 and HTTPS downgrades are rejected.

The worker makes outbound HTTPS requests to `/api/offline-downloads/worker/*`; it receives only one job and a dedicated worker key, never Dropbox OAuth or a NAV admin session. The API alone uploads 8 MiB chunks through the existing separately authorized personal connection and enforces the protected backup tree. No new public control port is opened. Full file size and Dropbox content hash must match before success. Only generated cache files for that job are deleted after confirmed completion or cancellation; cloud files are never deleted by worker cleanup.

Queue URLs are encrypted at rest using an AES-GCM key derived from the dedicated worker key. This is protection against accidental plaintext exposure, not against an attacker who controls both configuration and queue. The API's owner-only integration directory holds `offline-downloads.json` and `offline-jobs.json`; both require 0600 and the API UID. Schema: config version 1, enabled true, a random 64-hex workerKey and maxBytes 6442450944. Queue initialization must be explicit: missing, damaged or mismatched-key state fails closed, never silently resets work. Do not put configuration in Git, logs or chat.

Worker configuration is `/etc/nav-offline/worker.json`: version 1, apiBase set to an approved NAV origin plus `/api/offline-downloads`, the dedicated key, and directory `/var/lib/nav-offline`. Files and state directory belong to the worker UID with 0600/0700. Deploy one instance only in a constrained container with no ports, read-only root, dropped capabilities, no-new-privileges, 256 MiB memory and bounded CPU. Existing host services remain unchanged. Initial installation, key transfer and service start require a separately reviewed operation baseline and authorization.

Queue/cache survive API/worker restart. Provider upload sessions remain in API memory: an interrupted session may retransmit cached bytes after restart but strict-add never overwrites. A durable `committing` state is written before the final provider call; uncertain outcomes are held for manual review rather than repeated. Cleanup acknowledgements are retried without a second commit. Moving the backup folder or changing the connected account fails closed.

Unit/worker tests run through `api/test/offlineDownloads.test.js` and `api/test/offlineWorker.test.js`. The Vue harness uses only synthetic API responses. Real acceptance must use only an explicitly generated directory and synthetic file, with size/hash verification and scoped cleanup. Passing small-fixture tests is not evidence of a real 6 GiB movie transfer. BT, embedded Office and server transcoding are outside this resource-bounded worker.
