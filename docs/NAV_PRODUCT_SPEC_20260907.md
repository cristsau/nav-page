## 2. 产品定位与角色

DOMO NAV 是个人优先、兼顾小团队的私有工作台，服务“快速找到、及时记录、可靠整理、随时接续”。主导航保持导航、时光、图片库、助理四项，设置作为账号菜单入口；认证和后台运维服务这些日常任务。

| 角色 | 能力 | 限制 |
|---|---|---|
| 访客 | 登录、申请注册、找回密码、访问被主动公开的分享 | 无法检索私有内容或读取账号存在性 |
| 待验证 / 待审批用户 | 完成注册验证、了解申请状态 | 验证邮箱不等于审批通过；所有登录方法执行同一审批检查 |
| 已审批用户 | 管理自己的导航、笔记、图片、身份、设备及被授权的协作内容 | 后端逐项检查所有权与工作区权限 |
| 工作区协作者 | 按既有角色读写文档、数据库、评论 | 不能借搜索、AI、离线同步扩大权限 |
| 管理员 | 用户审批、系统集成、最小化审计和维护状态 | 权限判断在服务端，敏感操作需要近期密码复验 |

成功指标：登录和找回不再依赖数据库手工操作；常用收藏更易找到；移动端可完成所有日常操作；保存、同步和投递状态可信；误删除可预防，恢复可验证。

## 4. 认证与账号安全需求

### 4.1 登录入口

`/auth` 默认展示“邮箱验证码 / 账号密码”两个切换项。验证码能力全局未就绪时默认密码页，并说明验证码登录暂不可用。Google、微信仅在配置就绪且启用时出现，恢复码入口收纳到“无法登录？”中。

邮箱验证码登录流程：填写邮箱 → 申请验证码 → 输入验证码 → 服务端消费验证码并创建新会话 → 返回原页面。`redirect` 仅允许安全站内路径；不允许 `//`、反斜杠、凭据 URL 或外部地址。

仅匹配 `users` 中唯一、已审批、已验证绑定的邮箱。不得以昵称、相似邮箱、邮箱点号或 `+tag` 自动合并账号。未知邮箱不自动注册；申请入口独立。账号冻结 / 审批状态在验证码验证事务内再次检查。

### 4.2 老账号邮箱绑定与更换

这是验证码登录和找回的发布前置能力，不能只给新注册账号开放而让老账号继续依赖运维。

1. 未绑定邮箱：账号密码登录 → 近期密码复验 → 输入新邮箱 → 新邮箱验证码 → 原子绑定并设置 `email_verified_at`。
2. 已有邮箱但未验证：仍走上述复验和验证，不根据历史字段或 Google 返回值自动标记本地验证成功。
3. 更换邮箱：近期密码复验 + 原已验证邮箱的更换授权码 + 新邮箱绑定码，三项绑定同一请求；成功后旧邮箱、新邮箱均收到安全通知。
4. 原邮箱已不可用：保留受控账号恢复流程，验证所有权后处理；邮箱登录会话本身不能静默替换恢复邮箱。
5. 邮箱重复：数据库唯一约束兜底。只向本人提示“该邮箱无法用于此操作”，不暴露占用者身份。
6. 换绑成功：撤销其他会话、旧邮箱及当前账号所有未完成身份挑战；当前会话轮换。恢复码按已批准策略重新生成，旧码撤销。

复用已有邮箱规范化函数和 `LOWER(email)` 唯一索引，首轮先做只读冲突报告；不得在新认证接口单独引入不兼容的 Unicode / 大小写映射或自动改写历史邮箱。

### 4.3 已登录：通过邮箱验证码改密

设置 → 账号与安全 → 修改密码 → “邮箱验证码验证”。邮箱从当前账号的已验证绑定读取，前端不能提交另一个目标账号或任意收件人。未绑定时展示绑定引导，并保留“验证当前密码”方式。

流程：申请用途为 `password_change` 的验证码 → 填写验证码、新密码及确认密码 → 单次提交。事务成功后撤销全部会话（含当前会话）、当前账号全部未消费认证挑战和未用恢复授权，清除当前域 Cookie，回到登录页。两个域名均需重新登录。新密码不得与当前密码相同。

### 4.4 未登录：忘记密码

流程：输入绑定邮箱 → 申请用途为 `password_reset` 的验证码 → 提交验证码及两次新密码 → 完成后使用正常登录入口重新登录，不自动登录。

首期采用验证码与新密码在同一后端请求内验证提交，避免新引入可跨用途使用的长期 reset token。前端可分步展示，但不可在“下一步”时提前消费验证码。若未来增加独立授权 token，必须短时、一次性、用途隔离且不得放 URL。

成功事务：更新密码散列与时间 → 撤销全部会话、所有未消费认证挑战及有效恢复码 → 写安全事件 → 入队一封不含密码的改密通知 → 提交。通知真正投递失败不能撤回已完成改密；通知入队失败则事务失败，提示可重试。普通已登录密码改密也应统一撤销未消费挑战，避免旧找回码在改密后覆盖新密码。

**密码策略建议**：现有代码允许 12–1024（JS 字符串长度），继续支持现存密码登录；本期新注册 / 设置新密码统一为至少 15 个 Unicode 码点、最多 1024 个码点并限制 UTF-8 请求大小，所有入口一致。允许空格和粘贴，不静默 trim / 截断 / 改写密码，不强制字符组合；增加常见及泄露密码阻止策略并采用本地或隐私保护实现。现存短密码不批量锁定。继续调用现有 scrypt 工具，参数增强独立压测，不同时迁移散列算法。此为拟实施优化，不是现有密码策略已改变。

NIST 对单因素密码长度有新的基准，并不认可电子邮件作为其规定的带外认证器。因此本项目的邮箱登录应明确为便利的单因素方式，不能标榜 MFA、抗钓鱼或 NIST AAL2；邮箱也将成为账号恢复的信任根。[NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html)

### 4.5 Passkey 退役

第一批移除登录按钮、账号安全中的登记 / 列表、凭据自动填充 `webauthn` 标记、浏览器 WebAuthn 调用、帮助文案及活跃配置项；禁用底层路由，不能仅隐藏按钮。

`GET /api/auth/passkeys/config` 在兼容窗口返回固定 `{ enabled: false, retired: true }`；其他旧 Passkey 操作返回 `410 / PASSKEY_RETIRED`，且不查询或修改凭据。旧环境开关不能重新启用。前端第三方登录按钮的 `auth-passkey` 样式重命名，避免误删 Google/微信样式。

移除运行时路由接线及只服务 Passkey 的依赖；恢复码路由中对历史凭据的清理须与迁移兼容。旧迁移 `019`、`032`、历史表和备份保留，不改迁移台账、不立即 DROP 表。旧客户端收到 410 后展示升级说明并刷新认证能力配置；PWA 更新不得清空未同步业务数据。

正式禁用前核验：全部活跃账号至少有一种已验证可用替代路径，管理员必须实测；仅做替代路径覆盖统计，不导出凭据。业务功能取消与历史凭据物理销毁分开，后者在回滚窗口结束和明确保留策略后另批处理。

### 4.6 双域与身份 OAuth

两个域名共享账号和数据库，不共享 Cookie；在 A 域发起的验证码挑战只能回 A 域消费。用户可以在 B 域重新申请，挑战不能跨域互换。改密撤销数据库会话后，两域旧会话均失效；当前域主动清 Cookie，另一域在下一次请求 401 后清理本地状态。

Google 仅 `openid email profile`；身份唯一键是 Provider + subject。微信只使用受验证的 unionid/openid，不按昵称匹配。已有绑定不因 Passkey 退役或改密被删除。Google 已验证邮箱自动匹配继续默认关闭，本地邮箱验证不触发 OAuth 自动绑定。

必须逐条登记的 Google 回调（延续项目约束）：

- `https://nav.skrskr.net/api/auth/oauth/google/callback`
- `https://nav.cristsau.cn/api/auth/oauth/google/callback`

配置入口：设置 → 登录与系统集成 → 外部账号登录；详细步骤见 [Google 配置手册](./NAV_GOOGLE_LOGIN_SETUP.md)。SMTP 验证码不需要 Gmail 或邮箱 OAuth 权限。

## 5. 验证码协议与数据模型

以下接口、字段、参数都是设计提案；不得表述为当前可调用 API。路由保持 Fastify `/api` 前缀，响应不返回任何验证码、密码、散列或邮箱存在标记。

### 5.1 统一挑战规则

| 项目 | 首期拟定值 / 行为 |
|---|---|
| 验证码 | CSPRNG 生成 6 位十进制，含前导零；不可使用 Math.random |
| 有效期 | 创建起 5 分钟，以 PostgreSQL 时钟为准，发送重试不延长 |
| 重发 | 同一 browser flow / 用途至少间隔 60 秒；新码生成原子撤销该 flow 旧码 |
| 输入错误 | 每挑战最多 5 次，失败计数必须提交；不能随业务异常回滚计数 |
| 身份限流 | 规范化邮箱键跨域跨用途汇总：5 次/小时、10 次/日，所有请求同等计入 |
| 来源限流 | 每可信客户端 IP 10 次/10 分钟、50 次/小时；小团队共享出口需观测调优 |
| 验证限流 | 每 IP 20 次/10 分钟，叠加挑战 5 次上限；两实例共享 PostgreSQL 状态 |
| 总预算 | 全站发送预算初始 200 次/小时；结合服务商额度和用户量评审后配置 |
| 并行 flow | 同账号用途最多 3 个活跃 flow；新的陌生请求不得撤销其他设备有效挑战 |
| 密钥 | 独立版本化 OTP HMAC key，服务端 owner-only；不复用 SMTP 或 OAuth Secret |
| 存储 | HMAC-SHA-256(key, version/purpose/user/email/origin/challenge/code)，不保存纯 SHA-256 短码 |
| 一次性 | 挑战行锁 + 条件消费；并发 20 次正确提交最多一次成功 |
| 浏览器绑定 | 随机 flow secret 放 HttpOnly / Secure / SameSite Cookie；数据库只存 digest；挑战 ID 不具授权能力 |
| 响应 | 匿名申请对未知、未验证、未审批、有效邮箱一致 202 和相同结构；返回等长随机 challenge ID |
| 失败文案 | 消费失败统一“验证码无效或已过期”；全局不可用 503，来源限流 429 + Retry-After |

邮箱级限流、账号不可用等状态均在通用 202 路径处理，不向匿名客户端暴露具体原因；IP 429 的产生独立于目标账号是否存在。服务端异步入队并均衡快速失败分支，验收比较延迟分布；随机等待本身不是防枚举证明。申请找回不得冻结账号或撤销原有登录。

验证码输入使用一个语义完整的输入框，可视觉分组但不拆成六个强制跳转字段；支持粘贴、`autocomplete="one-time-code"`、`inputmode="numeric"`、前导零和读屏。不把验证码放在 URL、埋点、剪贴板自动写入或 Web Push 中。

这些账号枚举防护、一次性凭据、改密后通知与重新登录原则参考 [OWASP Forgot Password](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)；上表的时限和配额为本项目初值，不是 OWASP 强制数值。

### 5.2 API 契约

| 接口（拟新增） | 前置条件 / 请求 | 成功行为 |
|---|---|---|
| `GET /api/auth/capabilities` | 匿名；无秘密 | 密码 / 邮箱登录 / 邮箱改密 / 恢复码 / 已启用 Provider 能力及全局维护状态 |
| `POST /api/auth/email-login/request` | email；申请 flow Cookie | 通用 202：challengeId、expiresIn=300、resendAfter=60；不保证已收件 |
| `POST /api/auth/email-login/verify` | challengeId、code、flow Cookie | 校验并消费、建会话、轮换 Cookie；返回最小化 user |
| `POST /api/auth/password-reset/request` | email；独立用途 flow | 同一通用 202 格式；无账号状态回显 |
| `POST /api/auth/password-reset/confirm` | challengeId、code、newPassword、confirmPassword、flow | 原子改密，返回 ok、signInRequired=true；不自动登录 |
| `POST /api/auth/account/password/email/request` | 当前会话；服务端定位账号邮箱 | 发起 password_change 挑战；不接受 userId / 目标邮箱 |
| `POST /api/auth/account/password/email/confirm` | 当前会话、challengeId、code、两次新密码 | 统一改密事务及会话失效 |
| `GET /api/auth/account/email` | 当前会话 | 本人脱敏邮箱、verified、可用认证方式 |
| `POST /api/auth/account/reauth/password` | 当前会话、currentPassword | 用途限定、最多 5 分钟的服务端复验 grant；关联当前 session，Cookie 持有 |
| `POST /api/auth/account/email-change/request` | 当前会话、复验 grant | 已绑定账号只向旧邮箱发送换绑授权码；未绑定跳过此步 |
| `POST /api/auth/account/email-bind/request` | 当前会话、新邮箱、复验 grant；必要时旧邮箱挑战与 code | 消费旧邮箱授权并关联同一换绑 flow，发新邮箱验证挑战 |
| `POST /api/auth/account/email-bind/confirm` | 当前会话、challengeId、新邮箱 code、同 flow | 验证唯一性与身份版本后原子换绑、通知和会话轮换 |

接口方法和名称在开发前统一到 OpenAPI / Fastify schema；不使用通用 `purpose` 入参让匿名请求访问绑定或已登录改密用途。密码格式错误不消费验证码，但请求也计入来源限流；错误码校验失败要持久计次。

所有请求体 schema `additionalProperties:false`，认证写入维持精确 Origin / Fetch Metadata / CSRF 检查，未知或缺失来源按当前安全规则拒绝；只有独立受控客户端才使用专门契约。响应 `Cache-Control:no-store`，SW 不缓存、不离线排队这些请求。

### 5.3 PostgreSQL 设计

复用 `users.email`、`email_verified_at` 及唯一索引；复用会话、审计、共享限流。新增加法迁移，序号在分支整合时分配（当前目录已到 `046`，不能盲用可能被其他工作占用的编号）。

| 对象 | 建议字段与约束 |
|---|---|
| `auth_email_challenges` | id(UUID)、user_id(可空以容纳诱饵申请)、purpose(枚举)、email_key_digest、origin、flow_digest、code_mac、key_version、credential_version、expires_at、failed_attempts、consumed_at、revoked_at、created_at |
| `users.auth_version` | 默认 0；密码/邮箱/恢复状态变化递增，使旧挑战、复验 grant 与危险操作凭证失效 |
| `auth_reauth_grants` | id、user_id、session_id、purpose、credential_version、expires_at、consumed_at；不保存当前密码 |
| `auth_email_delivery_jobs` | id、challenge_id(可空外键；验证码任务必须有且唯一)、dedupe_key(唯一)、message_type、encrypted_payload、nonce/tag/key_version、state、attempts、next_attempt_at、accepted_at、expires_at；安全通知可不关联挑战，重试沿用原任务 |
| 既有 `sessions` | 可增 authentication_method / authenticated_at；不能以角色提升会话认证强度 |
| 既有 `security_events` | 补充固定事件白名单和最小化结果，不记录原始 code/email/password/body |

约束：expires_at > created_at；failed_attempts 0..5；未消费活跃索引；维护按 expiry / state 分批；挑战消费和副作用同事务。HMAC 输入必须使用无歧义编码而非无分隔字符串拼接，验证使用恒定时间比较。

验证事务固定锁顺序：先定位挑战所指用户，按 user → challenge → grant / session 锁定，重新核对邮箱、审批状态、auth_version、用途、origin、flow、有效期。重发 / 换绑 / 改密遵循同一顺序，避免死锁和重置覆盖。错误计次分支返回失败结果并 COMMIT，不能抛错触发计数回滚；基础设施失败才 ROLLBACK。

登录挑战消费与 session 创建原子提交。改密与身份变更一起增加 auth_version，使并发旧码无法继续操作。网络超时后的重复 confirm 返回失败或受同 flow 绑定的最小化“已完成、请登录”结果，绝不重复改密或重复建会话。

### 5.4 系统发信与秘密生命周期

当前 `mailOutbox.js::enqueueMail` 把正文写入 `text_body/html_body`；`sensitive` 布尔值本身不等于加密。**验证码邮件不得直接复用该明文正文写入路径。**

方案：在现有系统 SMTP 调度生命周期内新增独立认证投递队列 `auth_email_delivery_jobs`，复用 TLS transport、共享锁、配置解析和错误分类；不恢复旧邮箱 worker。代码验证码及收件人仅在专用加密载荷中，使用独立认证发信密钥 / key_version 和 AEAD，上下文绑定 job/challenge/type；DB 挑战表只存 HMAC。

新增固定系统类型：`auth.email.login`、`auth.password.reset`、`auth.password.change.verify`、`auth.email.bind`、`auth.email.change.verify`、`auth.password.changed`、`auth.email.changed`。扩展系统消息白名单及对应测试，不允许 `user.mail`、邮件摘要、任意收件人或任意 HTML 进入认证队列。注册旧验证链接首期保留独立逻辑和回归。

调度与投递要求：

- 申请事务只入队，不持有用户行锁等待 SMTP；活跃 API 进程负责有界调度，新实例共享数据库租约，不额外启用个人邮件服务。
- 发送前重新核对 challenge 状态和过期时间；剩余有效时间不足 60 秒则取消，不发送将过期码。已被重发替代、已消费、换绑或改密作废的任务均跳过。
- 若邮件已经进入 SMTP 在途阶段后挑战才被撤销，邮件仍可能到达；后端必须拒绝旧码，用户界面说明使用最近一次有效请求。不能承诺撤回已发送邮件。
- 初次发送尽快唤醒；网络暂时故障最多 3 次，建议间隔 10 / 30 / 60 秒且不超过有效期。SMTP 明确拒绝终止；DATA 后结果不明标记 unknown，不盲目重发或宣称已收件。
- SMTP 接受仅标 accepted，除非服务商提供可核验送达事件，否则 delivered 只能由实际收件验收认定。管理员面板只显示聚合计数 / 错误类别，不展示正文、码或收件人列表。
- SMTP 接受后清空应用数据库中的可解密短期验证码载荷；失败/取消/过期最迟 expiry 后 15 分钟清空；挑战审计元数据 24 小时后有界清理，非敏感事件按既有审计策略保留。
- WAL、旧备份可能仍含短期密文，必须纳入备份访问和密钥保留说明；不能把清空线上列宣称为备份中已物理擦除。灾难恢复启动前撤销过期挑战和未完成认证投递，防止恢复旧备份重发旧码。
- HMAC 与邮件加密 key 分离，轮换支持有限版本窗口；旧挑战最迟 5 分钟失效。密钥缺失/不可读时能力关闭并告警，不能退化为明文或默认密钥。

真实 SMTP 参数延续 owner-only 配置入口：`NAV_MAIL_DELIVERY_ENABLED`、`NAV_SMTP_HOST`、`NAV_SMTP_PORT`、`NAV_SMTP_SECURE`、`NAV_SMTP_USERNAME`、`NAV_SMTP_PASSWORD_FILE`、`NAV_SMTP_FROM_ADDRESS`。本文不读取真实值。拟新增独立开关 `NAV_EMAIL_LOGIN_ENABLED`、`NAV_EMAIL_PASSWORD_RESET_ENABLED` 和认证密钥文件路径，默认关闭；具体名称经 config schema 确认。

上线前核验固定发件域、证书、服务商限额及 SPF/DKIM/DMARC 配置，实际查看收件箱和垃圾箱分类；TLS 连接成功不替代收件验收。验证码主题明确“登录 / 修改密码 / 绑定邮箱”，正文显示用途、发起域、5 分钟期限和“请勿转告他人”，不包含新密码或营销信息。

### 5.5 敏感操作与审计

邮箱登录具有与账号相同的业务权限，但修改邮箱、绑定 / 解绑第三方身份、导出私有数据、恢复数据、生成恢复码和管理员系统配置延续或补齐近期密码复验；授权 grant 限当前操作、当前会话、当前 auth_version，不因一次验证码登录无限授权。此为项目权限设计，参考 [OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)。

建议事件：`auth.email.login`、`auth.password.reset`、`auth.account.password.update`、`auth.account.email.bind`、`auth.account.email.change`、`auth.passkey.retired`。成功业务审计与变更同事务；失败审计限量聚合，避免攻击者撑满磁盘。日志层明确屏蔽认证 body、Cookie、验证码、密码、收件人和 SMTP 原始载荷。

### 7.4 可访问性、响应式与性能目标

目标覆盖 WCAG 2.2 AA 的相关交互要求：文本对比、键盘、焦点、错误提示、重排和可访问认证；实际合规仍需完整审查。普通文字至少 4.5:1、大字及必要非文本界面元素至少 3:1；触屏目标采用项目更严格的 44×44 CSS px（不是把 AA 的 24px 最小目标误写为 44px）。支持粘贴和密码管理器。[WCAG 2.2](https://www.w3.org/TR/WCAG22/)

验收宽度 320 / 390 / 768 / 1024 / 1440；横屏、200% 缩放、320px 重排不横向溢出；iPhone 键盘、安全区和底栏不遮挡验证码提交。桌面 Chromium/Firefox/Safari 与真实 iPhone Safari/PWA 都要记录版本。

性能拟定门槛：受控 390px、移动网络/CPU 限速、合成账号与固定数据，5 次冷启动中位 LCP ≤2.5s、CLS ≤0.1；真实样本足够时按 p75 检查 INP ≤200ms，样本不足只报实验结果。登录页不得加载块编辑器/AI/历史邮件重包；首屏 JS gzip 目标 ≤180 KiB（不含独立懒加载模块），记录当前基线后执行预算。1,000 收藏 + 1,000 笔记合成数据，普通列表操作 p95 ≤200ms；必要时分页/虚拟化，不默认升级框架。

Core Web Vitals 指标阈值参考 [web.dev 官方说明](https://web.dev/articles/vitals)；实验条件、包体积预算和数据集为本项目验收设计。

## 10. 可执行验收标准

优先级：P0 = 上线阻断；P1 = 对应批次阻断；P2 = 有记录可排后。下面都是待执行用例，不是已通过结果。每条记录 commit、环境、时间、输入类型、预期、实际、证据路径与执行人；认证证据只能用合成账号和脱敏结果，不截图码或密码。

### 10.1 账号与验证码（R1 全部 P0）

| ID | 场景 / 操作 | 必须满足的结果 |
|---|---|---|
| A-01 | 老账号、未验证、重复邮箱基线 | 有安全覆盖统计和冲突处理清单；无静默改写、无未验证邮箱自动启用 |
| A-02 | 已审批已绑定账号在双域各走验证码登录 | 回到同一 user；会话按域隔离，角色不变，原内容可见 |
| A-03 | 未知/未验证/未审批/冻结邮箱申请 | HTTP、字段、长度级别一致，无 exists/email/status 泄露，无自动建号或审批 |
| A-04 | 在发码后冻结账号/更换邮箱 | 验证事务拒绝；旧码不能恢复访问或定位到新邮箱 |
| A-05 | 验证码不足/超长/非数字/前导零 | 严格 schema，前导零保留；非法请求不进入身份写入 |
| A-06 | 创建后 299s 与 300s、跨服务器时钟偏差 | 以数据库到期值判断；未到期按其他条件验证，到期拒绝 |
| A-07 | 5 次错误码再尝试正确码 | 计数持久化，挑战锁死；账号原有密码仍可登录 |
| A-08 | 同一正确码并发提交 20 次 | 最多一次成功、一次 session/改密与审计；其他均拒绝 |
| A-09 | 登录码用于改密/换绑/注册，A 域码用于 B 域 | 全部拒绝，不产生副作用 |
| A-10 | 重发、两个设备、多标签、攻击者请求 | 同 flow 旧码失效；其他合法 flow 不被陌生申请撤销；限额生效 |
| A-11 | 多实例、重启、换 IP、双域配额 | PostgreSQL 共享限制不重置；可信代理 IP 解析不可伪造 |
| A-12 | 申请成功后 SMTP 明确失败、超时或结果不明 | 正确队列状态，无假“已收件”、无无限重试，密码入口可用 |
| A-13 | 队列积压到码过期、改密后旧任务、重发旧任务 | 不投递无效码，重试不延长有效期 |
| A-14 | 检查 DB、日志、管理员 API、导出、SW、IndexedDB | 无验证码/密码明文和授权凭据；短期载荷仅 AEAD 密文且按期清空 |
| A-15 | 缺失/错误/轮换认证密钥，HMAC/AEAD 篡改 | 失败关闭，无默认密钥/明文降级；版本边界明确 |
| A-16 | 已登录验证码改密、当前密码改密 | 新密码可登录、旧密码失败；两域全部旧会话和旧挑战失效 |
| A-17 | 未登录验证码找回 | 改密成功后未自动登录；恢复码撤销；安全通知仅发元信息 |
| A-18 | 两次新密码不一致、等于旧密码、Unicode 边界 | 无写入；统一策略；允许管理器粘贴、不 trim、不截断 |
| A-19 | 首次绑定、邮箱被其他账号占用 | 必须本人近期密码复验+新邮箱证据，唯一约束兜底，无身份信息泄露 |
| A-20 | 换绑时缺旧邮箱码/新邮箱码、复验过期 | 缺任何必要证据均拒绝；grant 不跨用途复用 |
| A-21 | 换绑成功与其他请求并发 | 邮箱和版本原子变化，旧挑战/其他会话失效，旧新邮箱通知入队 |
| A-22 | 邮箱登录后做导出/恢复/解绑/系统配置 | 后端要求对应近期密码复验，前端隐藏不作为安全边界 |
| A-23 | 旧 Passkey 页面/客户端/强开配置 | config 固定 disabled，所有操作 410，无 WebAuthn 调用、无新凭据记录 |
| A-24 | 错误 Origin/CSRF/伪造 flow/恶意 redirect | 全部拒绝；Cookie Secure/HttpOnly/正确 SameSite、auth no-store |
| A-25 | DB 错误或审计/通知入队故障注入 | 认证业务事务完整回滚；验证失败计次仍正确，不半改密 |
| A-26 | 管理员及全部活跃账号替代路径检查 | 禁用 Passkey 前有可用路径；管理员真实登录与恢复路径已验证 |

## 11. 发布、回滚与运维步骤

1. **候选冻结**：核对当前分支与 master / 已部署 merge 的包含关系；以正确主线建立候选并保留既有 dirty。不得直接把旧分支 HEAD 当新发布版本。补齐 CI、源码映射、依赖与迁移清单。
2. **授权前材料**：列精确 API/Web 服务、镜像 SHA、配置键、加法迁移、影响用户、已验证备份、容量预算、两批发布窗口及回滚命令草案。生产发布/迁移/配置启用在具体方案获授权后执行；文档交付不等于已部署。
3. **备份与容量**：CURRENT 的剩余磁盘是历史记录，现场核对镜像拉取+数据库备份+隔离恢复峰值需求和安全余量。不足则先精确规划扩容或获授权清理，不执行广泛 prune，不触碰未知卷和其他应用。
4. **加法迁移与灰度**：新代码默认 OTP 开关关闭；迁移后先启用测试/限定用户路径并完成实际收件与恢复；以管理端明确策略提供灰度，无公开账号名单。
5. **原子切换**：仅指定 API/Web 到精确 release；系统认证投递使用新 API 生命周期，不启动旧个人邮件 worker。Passkey 在替代路径验收后禁用，应用代码固定退役。
6. **失败处理**：认证不稳定优先全局关闭验证码申请/消费和认证投递，让密码和恢复码继续工作；记录所有未消费挑战失效。回滚使用“邮箱退役、Passkey 退役兼容版”的固定镜像；不能盲回旧 release 再开启已取消 Passkey。M3 必须构建并验证该回滚候选。
7. **数据回滚原则**：通常只回滚应用与开关，保留加法表；不恢复整库覆盖用户新数据，不重新启用旧会话/码。DDL 缺陷走前向修复；数据库恢复仅限明确灾难场景和独立方案。
8. **收口**：双域/收件/真机签收、24–48h聚合观察后更新 CURRENT 和发布台账；旧表和临时运维助手的留存/销毁列单独精确清单，经保留与恢复门槛后处理。

拟定运维指标：挑战申请/成功/过期/限流数量，认证请求 p95、队列最老等待时间、SMTP accepted/failed/unknown、短期密文清空时延、DB 连接池和存储趋势。报警内容只包含类型和计数；不能把账号邮箱作为监控高基数标签。
